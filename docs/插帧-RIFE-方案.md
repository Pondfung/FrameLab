## 一、实测性能（本机 RTX 5060 Ti）

测试方式：`rife-ncnn-vulkan` 官方预编译版（20221029）+ `rife-v4.6` 模型，1920×1080 输入，目录模式连续处理，统计稳态吞吐。

| 测试 | 输入帧数 | 输出帧数 | 总耗时 |
| --- | --- | --- | --- |
| 短跑 | 21 | 42 | 1.48 s |
| 长跑 | 201 | 402 | 5.16 s |

用两次测量做两点法（21 张 → 插 20 帧；201 张 → 插 200 帧）：

- 斜率 = (5.162 − 1.482) / 180 = **20.4 ms / 插帧帧**
- 截距 ≈ 1.07 s，是固定开销（Vulkan 初始化 + 模型加载 + 首个 shader 编译）

> 修正：早期版本这里写的是 10.7 ms，那是把"输出帧数 402"当成了"插帧次数 400"算出来的错值。实际 201 张输入只产生 200 次插帧，真实吞吐是 **20.4 ms/帧**。

换算：
- 1080p 吞吐 ≈ **20.4 ms**（同步调用延迟 24.8 ms）
- 720p 实测 ≈ **9.5 ms**、960×540 实测 ≈ **5.6 ms**（见第八节）

## 二、为什么用 ncnn 而不是 TensorRT

| 项 | ncnn-vulkan | TensorRT |
| --- | --- | --- |
| 需要装什么 | 什么都不用装（vulkan-1.dll 系统自带） | CUDA Toolkit（约 3 GB）+ TensorRT（约 1 GB） |
| 模型 | 官方提供 `.param`/`.bin`，即取即用 | 需要自己从 PyTorch 导出 ONNX 再 engine 化，且 engine 绑定显卡型号 |
| 首次启动 | 立即 | 需要 build engine（分钟级） |
| 速度（1080p） | ~10 ms | 预计 4–6 ms |
| 集成方式 | C++ 静态库 + FFI | C++ 动态库 + FFI |

**结论：先用 ncnn 把功能做出来**。10 ms/帧已经够 30→60 插帧（预算 16.7 ms）。TensorRT 作为后期提速选项，等真正跑起来发现瓶颈再说。

本机现状：无 CUDA Toolkit、无 TensorRT、无 Vulkan SDK，但有 `vulkan-1.dll`（驱动自带运行时）——正好是 ncnn-vulkan 唯一需要的东西。

## 三、和 VSR 组合的算力账

这张卡 1920×1080 只有 **30 fps**，720p 才有真 60 fps。所以最合理的组合是：

> **1080p30 → RIFE 插到 60fps → VSR 超分到 1440p**

每秒的 GPU 工作量：

| 步骤 | 次数/秒 | 单次耗时 | 合计 |
| --- | --- | --- | --- |
| RIFE 插帧（**1080p**） | 30 | 24.8 ms | 744 ms |
| RIFE 插帧（**720p**） | 30 | 9.5 ms | 285 ms |
| VSR 超分真实帧（1080p→1440p，档 2） | 30 | 3.46 ms | 104 ms |
| VSR 超分插帧帧（同上） | 30 | 3.46 ms | 104 ms |

两种配置的合计：

- **1080p 插帧 + VSR 档 2** = 744 + 208 ≈ **952 ms/s（95% GPU）** —— 跑不动，没有余量。
- **720p 插帧 + VSR 档 2** = 285 + 208 ≈ **493 ms/s（49% GPU）** —— 舒服，还能开 VSR 档 3。

**结论：RIFE 只适合 720p 源。**

> 2026-11-23 补记：上面的「工作分辨率」机制随后被移除——插帧一律在采集分辨率上做，
> 因为缩到 720p 再放大回 1080p 是净损失（细节在缩小那步就没了）。1080p 的插帧需求
> 改由 FRUC 引擎承担（6.4 ms，见 `docs/插帧-FRUC-方案.md`），RIFE 保留给 720p 源追画质。

反过来若源是 60 fps 想做 120 fps（720p 场景），成本翻倍到接近满载，不推荐默认开启。

延迟代价：
- RIFE 需要下一帧才能生成中间帧 → **+1 帧（33 ms）**
- VSR 单帧 3–9 ms
- 合计约 +40 ms

## 四、集成方式

### 4.1 组件

```
livecard/
  crates/rife/                新增
    build.rs                  编译 C++ wrapper
    src/lib.rs                Rust 侧安全封装
    cpp/rife_ffi.cpp          ncnn 调用封装（C ABI）
    cpp/rife_ffi.h
    third_party/ncnn/         ncnn 预编译库（Windows x64, vs2022）
    models/rife-v4.6/         flownet/contextnet/fusionnet 的 .param + .bin
```

### 4.2 C ABI 设计

```c
// 一次性初始化，加载模型到显存
void* rife_create(const char* model_dir, int gpu_id);
// 两帧 RGB24 输入 → 一帧 RGB24 输出；timestep 固定 0.5
int   rife_interp(void* ctx, const unsigned char* f0, const unsigned char* f1,
                  unsigned char* out, int w, int h);
void  rife_destroy(void* ctx);
```

内部要点（抄 rife-ncnn-vulkan 的做法）：
- 输入 RGB24 需转成 ncnn 的 `Mat`（float，pixel 范围 0–1），并 pad 到 32 的倍数。
- RIFE 的 ncnn 实现是三个子网络串联：`flownet` → `contextnet` + `fusionnet`，各用独立 `ncnn::Net`，**共享同一个 `VkDevice`**（ncnn 的 `create_gpu_instance` 全局单例）。
- 每帧复用 `ncnn::Extractor`，避免反复申请显存。
- 用 `ncnn::VkAllocator` 做显存池，防止 60 fps 下的分配抖动。

### 4.3 与 wgpu 的数据流

ncnn 走 Vulkan，wgpu 走 DX12，**目前只能 CPU 往返**：

```
采集帧（CPU 内存）→ RIFE（CPU→GPU→CPU）→ wgpu 上传渲染
```

1080p RGB24 = 6 MB/帧，60 fps 就是 360 MB/s 的上传量。PCIe 4.0 x16 理论 32 GB/s，实际 map/copy 约 2–3 GB/s，**占用约 15%**，可接受但不是零成本。

> 未来优化：把 ncnn 的 Vulkan 后端换成和 wgpu 相同的 Vulkan 设备（`VK_KHR_external_memory_win32` 共享纹理），可以做到零拷贝。这一步等有性能数据后再决定要不要做。

### 4.4 中断与异常处理

- 场景切换（画面剧变）：RIFE 会糊。检测方法是对比输入帧的直方图差异，超过阈值直接输出前一帧（透传）。
- 显存不足：`ncnn` 返回错误时降级为不插帧，并在面板提示。
- 断流重连期间：跳过插帧，避免用旧帧凑数。

## 七、风险

1. **ncnn 版本与 Blackwell 的兼容性**：当前实测的 2022 年版 ncnn 在 5060 Ti 上跑通了，说明基础路径没问题；但集成时建议用较新的 ncnn（2024+）以获得更好的新架构优化。
2. **Vulkan 后端在多线程下与 wgpu 的 DX12 共存**：理论上互不干扰（不同 API），但需要实测确认不打架。
3. **CPU 往返带宽**：1080p60 下 360 MB/s，若同时做 VSR 可能翻倍，需要监控。
4. **首帧延迟**：模型加载约 0.5 s，应在启动时异步预热，避免第一次开插帧卡一下。

## 八、自建 ncnn 封装实测（2026-11-23）

### 环境

- ncnn 20261020（Windows vs2026 shared 包，自带 Vulkan 后端）
- rife-v4.6 模型（`flownet` 的 `.param`/`.bin`，v4 已把 contextnet/fusionnet 合并进 flownet）
- 自己写的 `rife_ffi.cpp`（C ABI）直接复用 `rife-ncnn-vulkan` 的 `rife.cpp` / `warp.cpp`

### 需要打的两个补丁

`rife-ncnn-vulkan` 的源码是为老版 ncnn 写的，配新版编译需要改 `warp.cpp`：

1. 顶部加 `#define NOMINMAX`——否则 `windows.h` 的 `min`/`max` 宏会破坏 `std::min/std::max`。
2. `opt.use_shader_pack8` 在新版 `ncnn::Option` 里已被移除，改为 `if (false)` 只走 pack4 分支（实测输出正确，性能未见明显损失）。

另外 `warp.cpp` 用到 `.comp` 着色器，需要把 GLSL 源码转成 `xxx.comp.hex.h`。CMake 里那段 `generate_shader_comp_header.cmake` 只是**把文本转成十六进制数组**（运行期由 ncnn 自己编译），用十几行 Python 就能复现，不需要装 Vulkan SDK。

### 结果

| 项 | 数值 |
| --- | --- |
| GPU 识别 | RTX 5060 Ti，`fp16-p/s/u/a=1/1/1/1`、`rebar=1` |
| 模型加载（含首次 shader 编译） | 4.33 s |
| 单帧插帧（1080p，同步等待） | **24.8 ms** |
| 输出正确性 | 方块中心：帧0 = 330 px，帧1 = 370 px，插帧 = **349.7 px**（理论 350） |

### 关于"24.8 ms vs 官方 10.7 ms"

两个数不是同一个指标：

- **10.7 ms** 是官方 CLI 用 `-j 2:2:2` 三线程流水线的**吞吐**（读、算、写重叠，GPU 不等 CPU）。
- **24.8 ms** 是我们同步调用的**单帧延迟**（提交 → 等 GPU → 拿结果）。

ncnn 的 `Extractor::extract` 内部会阻塞等待，所以单实例无法简单异步。要拿到吞吐量需要多实例轮转或多缓冲，属于后续优化项。

### 三线程流水线到底有没有用

官方 CLI 的 `-j load:proc:save` 是三个阶段并行：读图解码（CPU）、GPU 推理、写图编码（CPU）。同一批 201 张输入、同一模型：

| 线程配置 | 总耗时 |
| --- | --- |
| `-j 1:1:1`（全串行） | 5.88 s |
| `-j 2:2:2`（默认） | 5.16 s |
| `-j 4:4:4`（加线程） | 5.38 s |

**差异只有 ±7%**。原因是这条流水线隐藏的是 jpg 编解码这类 CPU 工作，而瓶颈始终在 GPU 的 20 ms 推理上。LiveCard 里根本没有图片编解码（帧直接从采集卡和显存来），所以**这个流水线对我们没有意义**——搬过来只会增加复杂度，不会更快。

### 不同分辨率的实测

| 分辨率 | 单帧（同步） |
| --- | --- |
| 1920×1080 | 24.8 ms |
| 1280×720 | 9.5 ms |
| 960×540 | 5.6 ms |

基本按面积缩放，说明是纯 GPU 计算受限，而不是带宽或调度。

### 性能预算（关键结论）

1080p30 → 1440p60，**每 33 ms 一周期**：

| 配置 | 每周期耗时 | GPU 占用 |
| --- | --- | --- |
| 1080p 插帧 + VSR 档 1 | 24.8 + 2×2.86 = 30.5 ms | 92% |
| **720p 插帧 + VSR 档 2** | 9.5 + 2×3.46 = 16.4 ms | **50%** |

1080p 插帧虽然还挤得下，但 92% 占用意味着任何波动都会掉帧；**720p 插帧是明显的甜点**，画质损失在运动帧上几乎看不出来（插帧本身处在两台原始帧之间，视觉上本来就带运动模糊）。

想要 1080p 插帧还留余量，只有换后端：TensorRT 预计 5–8 ms（需装 CUDA Toolkit + TensorRT 约 4 GB，本机尚未安装）。

## 九、落地实现（2026-11-23）

代码已进仓库，形态是「独立工作线程 + 帧序列倍增器」。

### 为什么放在工作线程

720p 一次插值 11.4 ms，加上 NV12 缩放（约 1 ms）和 NV12↔RGB 转换（约 5 ms），单个源帧要 18 ms。
如果塞进 UI 线程，egui 的重绘间隔会被拉到 33 ms 以上，插出来的 60 fps 序列根本播不出去，等于白做。

### 数据流

```
采集线程 ──NV12 1080p──▶ app.pump（UI 线程）
                            │
                            ├─ 开插帧：丢给 rife 线程，同时每帧从输出队列取一帧显示
                            └─ 关插帧：照旧直接塞进渲染 slot

rife 线程：NV12 1080p ──最近邻缩放──▶ NV12 720p ──BT.709──▶ RGB24
                                                              │
                    上一帧 RGB ◀──────────┬───────────────────┘
                                          ▼
                                    rife_interp(t=0.5)
                                          │
                                          ▼
                        RGB24 ──BT.709──▶ NV12 ──▶ 输出队列 [原帧, 插值帧]
```

`app.pump` **每帧**都从队列取一次（不是每来一帧源帧取一次），这样 UI 的 60 fps 重绘才能把
「原帧 / 插值帧」交替播出去。第一版写成"有新帧才取"，结果只能跑 30 fps，白插。

### 延迟代价

必须等下一帧到达才知道要插哪两帧之间，所以画面比采集多晚一帧（约 33 ms）；
再叠加超分的"延后一帧"，两者同时开启时画面晚约 66 ms。**声音是立刻播的，所以会听到声音领先画面。**
这个缺口目前只能靠人耳接受，或者把超分关掉（只晚 33 ms）。

### 实测（RTX 5060 Ti）

| 组合 | 显示帧率 | 插帧耗时 | GPU 占用 | 显存 |
| --- | --- | --- | --- | --- |
| 仅插帧 720p | 60 fps | 17.8 ms | 35% | 1930 MiB |
| 插帧 720p + VSR 档 2（→1440p） | 60 fps | 18.3 ms | 41% | 2102 MiB |

比预估的 50% 还宽裕，说明瓶颈主要在 CPU 侧的像素转换，GPU 还有余量。

### 三个坑

1. **`LoadLibraryExW` 必须在中文路径上先 `canonicalize`**
   `E:\小软件\...` 这种路径直接传给 `LOAD_WITH_ALTERED_SEARCH_PATH`，`ncnn.dll` 会找不到（`0x8007007E`）。
   转成 `\\?\E:\...` 形式就正常了。同一个坑在 VSR 上没暴露，因为 `nvngx_vsr.dll` 是从驱动目录找的。
2. **输出队列要限长**（当前 4 帧）。UI 偶尔掉帧时，队列会用越来越旧的帧堆积，表现为延迟越用越大。
3. **插帧失败要放行原帧**。否则一次插值失败就黑屏，看起来像死机。

### 什么时候不该开插帧（2026-11-23 补充）

这张卡 **720p 本身就是真 60 fps**。在 720p 档开插帧，实测是这样：

| 指标 | 实测 |
| --- | --- |
| 显示帧率 | 106 fps（egui 重绘不受 vsync 约束，自己飙上去了） |
| 插出来的帧 | 占一半，全是合成出来的假帧 |
| 插帧耗时 | 19.6 ms/帧（60 帧/秒地烧 CPU） |
| 净收益 | **负的**：更糊、多 33 ms 延迟、白烧 CPU |

真正适合插帧的只有 **1080p 档**：这张卡 1080p 只有 30 真实帧，插到 60 才有意义，
代价是工作分辨率降到 720p（画质换流畅）。想要画质就用「插帧 + 超分」组合，720p 插完再 VSR 回 1440p。

所以工作线程里加了源帧率检测：**实测源帧率 ≥ 50 fps 时默认直接透传**，
参数区显示 `插帧已跳过（源实测 60 fps，本身已够流畅）`。

但**高刷新率屏幕上是另一回事**：60 fps 的内容放到 180 Hz 屏上依然只有 60 的流畅度，
这时候把 60 插到 120 是有实际收益的。所以面板里给了「源已 60 fps 时也插帧」的开关
（`rife_force`），由用户自己决定要不要为流畅度牺牲质量。

显示端不再写死 60 fps，改成队列驱动：队列里有两帧就立刻取，没有才等 6 ms。
这样跟上插帧的实际产出速度，高刷屏能跑多少就跑多少。

> 2026-11-24 补记：上面这套「源 ≥ 50 fps 就跳过 + 攒两帧再出」已经换掉了。
> 现在插帧由**目标帧率**驱动（`settings.interp_target_fps`，0 = 跟随显示器刷新率），
> 倍率按 `target / 源帧率` 算，上限 2×（光流一次只补一帧）；源已经达到目标就直通。
> 显示端按 `1/target` 间隔出帧，不再攒两帧。`rife_force` 语义改成「强制两倍，忽略目标帧率」。

### 高刷实测（180 Hz 屏）

| 采集 | 插帧分辨率 | 单帧耗时 | 输入处理 | 显示帧率 |
| --- | --- | --- | --- | --- |
| 1080p @30 | 720p | 18.5 ms | 全处理 | 60 fps |
| 720p @60 | 720p | 18.0 ms | 52/60（丢帧） | 113 fps |
| 720p @60 | 540p | 10.0 ms | 60/60 | **120 fps** |

540p 刚好卡在"每个输入帧都能处理完"的线上（60 × 10 ms = 600 ms/s）。
再往上就要 3 倍插帧（60 → 180，每个输入帧算两次插值），540p 要 20 ms/输入帧，
1200 ms/s 超载，当前架构做不到。

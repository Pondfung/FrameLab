# VFG 错帧优化推进计划

日常导出支持纯 VFG High、纯 VSR Ultra 和 VFG → VSR → NVENC。2026-11-26 起，两个版本共用实现，CLI 提供 SDK 切镜的对照开关。产品范围和超分对照见 [选型与开发计划](离线视频超分与插帧-选型与开发计划.md)。

## 正式版本与短测基线

- 完整版使用 PyTorch，NVIDIA 单 EXE 使用 CuPy。两者共用按显式时间点调用 VFG High 的实现，正式导出默认启用 SDK 自动切镜。CLI 支持手工切点和 FFmpeg 场景分数阈值。 [快速导出实测](VSR与VFG-快速导出开发计划.md)
- 1126 录屏的 60→120 片尾报错已修复。完整版得到 1080p120、8,378 帧，3,273 个 AAC 包的内容和时间戳逐包一致。精简版通过同源片尾短样验证，取 24 张源帧输出 48 张。
- 旧成片中，60→120 筛出 382／4,188 张接近前后原帧的插帧（9.1%），30→120 为 950／6,279（15.1%）。这两个比例是缩略图筛查结果。单独切换 SDK 自动切镜，抽测中复现的 12＋32 张复制帧在关闭后都有了不同的画面。4× 约 11.8 秒曾连续停住 4 帧。两张可对上真实中点的候选亮度误差有下降，快速运动的轮廓与错位仍需复核。
- 韩信 24→96 中，4.625 秒和 14.000 秒是两处硬切前的最后一张原帧。新镜头首帧是零基帧 112、337，分别位于 4.6667 秒、14.0417 秒。9.0625 秒是同镜头坏帧。关闭 SDK 自动切镜的短测中，5 个同镜头区间的 9 张重复插帧均通过运动复检。早期只尝试倒序重算的短测中，7 个触发区间有 3 个通过。

## 生成帧复检

`run --vfg-review` 在编码前检查 VFG 生成帧。先插帧后超分的串联在显存中的 VFG 输出进入 VSR 前取样。GPU 只额外回读 320×180 取样，原图仍走已有导出路径。复检结果写进分段回执，暂停续跑复用已校验的记录。导出完成时生成 `.job/vfg-review.json`，报告按零基输出帧号列出源帧对、插值位置、相对导出起点的精确时间和判定依据。复检只记录疑似异常，照常导出。

用 BT.709 亮度比较。锚点亮度差达到 2 灰阶时，候选到锚点或同区间相邻生成帧的差在 0.85 灰阶和锚点差 10% 以内，即记录疑似复制或生成帧连续重复。聚合时将连续至少三帧的同锚点停帧合并，能跨分块统计。按时间倒序匹配锚点，或同一源帧对的相邻生成帧有至少三条可靠纹理匹配支持逆向运动时，记录疑似回跳。切镜与导出末尾持帧、原片定格和低运动槽位另计。局部回跳复检至少需要两张相邻生成帧，2× 主要覆盖锚点复制。大位移、遮挡和局部错位需要逐帧复看。

## 单次倒序重算

`run --vfg-retry` 隐含复检。锚点差至少为 2 灰阶、原生成帧与任一锚点差不超过 0.25 灰阶、插值位置在 0.20 至 0.80 时，交换锚点并以 `1−t` 请求一次。重算帧须与锚点保有差异，且至少有 18 个双向光流点支持目标位置，覆盖至少三块画面区域。只有通过复核才在送入 VSR 或编码前替换。保留已拥有的原输出张量，拒绝时使用原生成帧。报告的 `retries` 保存尝试和证据，`suspects` 是最终输出候选的复检结果。算法版本随分段回执持久化。桌面的纯 VFG 和 VFG → VSR MP4 导出会生成复检报告。导出中自动采用倒序结果可从 CLI 试用。

RTX 5070 上，韩信 24→96 沿用 10 个切点并开启 SDK 自动切镜。116 张疑似复制中有 27 张通过倒序重算的接受规则，包含 9.0625 秒。这里统计程序采用的候选数；视觉修复率需要逐段人工复看。88 张重算后仍接近锚点，1 张缺少足够的运动证据。连续同锚点停帧从 38 段降到 22 段。整片耗时 67.48 秒，先前只报告为 55.74 秒。音频包内容和时间戳、视频包时间戳保持一致。两版对同一短片跑 VFG → VSR → NVENC，完整版 7 源帧分块，单 EXE 4 源帧分块并暂停续跑，最终报告一致。另用自动切点扫描通过含源帧 112 硬切的串联短样。

1126 原 20→60 真帧对照中，6 张接受帧的亮度误差全部下降。另从韩信和 1126 的原始连续帧抽帧，257 个时间槽中共接受 9 张，8 张更接近真帧，1 张误差从 11.86 增至 15.24 灰阶（1126 原帧 1276）。双向光流仍可能只解释画面的一部分。维持试验开关，优先验证独立切点方案能否减少触发，再复核遮挡和回跳。逐帧证据见本机 `H:\video test\超分插帧测试\VFG-reverse-v1` 的 `assessment.json` 和 `holdout.json`。

## 人工复核与局部补跑

2026-11-26 内核复核结论：ABA 回跳和连续停帧已有可定位的样例，适合先做人工选段修复。严重拖影保留人工试修入口。1126 输出帧 311 上的多引擎候选均偏离真帧，拖影标签本身无法指明哪个候选更好。

- **标记。** 导入视频后从主播放器左上角进入「复核模式」，原位退出。已有导出时可另点「复核导入视频」选择原片。可以正常速度连续播放、逐帧步进、拖动时间轴，以及从复检报告跳转。「标记当前帧」记录画面实际显示的零基帧号。用两个下拉分别填写坏帧类型和镜头类型。黄色短线显示等待修复预览的标记，生成成功后原位变绿。标记和预览索引保存在原作业目录或视频旁的 .review 目录。 [前端实现](../desktop/src/review.rs)
- **推断范围。** 连续静止先匹配复检报告中的停帧段，再取其中可替换的插值槽位。ABA 可扩展到同一源帧对内同时被报告确认的回跳帧。旧作业没有报告或报告未覆盖标记位置时，连续静止通过附近画面相似度尝试扩展，再过滤原帧与持帧。严重拖影或缺少可靠证据时只处理标记帧。已记录的切镜、片尾持帧和原帧受保护。SDK 内部切镜没有位置列表，属于人工复核范围。
- **触发候选。** ABA 和连续静止优先 VFG 倒序。拖影先试 RIFE 4.25，高速拖影先试 GIMM-VFI。用户可改选候选模型，选择保留时仅记录。完整版的 RIFE 按源帧对和目标分数时间生成，时间分母大于 256 时改试其他候选。局部 GIMM-VFI 的输入像素以 1280×720 为上限，按原宽高比缩小，预测后恢复源尺寸再交 VSR 或编码。NVIDIA 单 EXE 使用 VFG 倒序。
- **生成与对照。** 串联路径先替换插值槽位，再送 VSR。重建受影响的编码块并校验。其他块同卷用硬链接复用，跨卷复制已编码块。候选重新封装后自动回到主播放器，按同一帧号切换「修复前／修复后」。候选 MP4 和 review-selection.json 留在原作业目录内，便于续跑和复核。 [分块与回执](../jobs.py)


直接导入旧成片时，匹配同名 .job 的已完成记录后复用原片、切点、时间轴和编码块。无作业记录的逐行 BT.709 SDR CFR 视频可用 `review-import <视频> <帧号> <副本.mp4> --choice reverse --label freeze`。这种模式用标记两侧的邻近帧作锚点，对连续相似的停帧扩展范围，遇到疑似切镜或缺少两侧锚点时停止修复。推理只处理所选坏帧，生成 MP4 预览时重新编码整条视频，并流复制兼容音轨和字幕。

旧的 1126 30→120 成片从留存的 88 个编码块恢复，SHA-256 与原回执一致。以输出第 1417 帧作为停帧标记，推断出的重算槽位是 1415、1417、1418。原帧 1416 保留。8,376 帧的显示时间戳和 AAC 包与修复前一致。

## 何时引入局部修复模型

保留 RIFE 4.25 和 GIMM-VFI 权重。FrameLab 的两条常规适配当前均按 2× 取中点。本轮用独立的 VapourSynth 测试验证 RIFE 4.25 与 4.26 能用同一原帧对请求 `1/3`、`2/3`。FixDeadFrame 已有按时间点批量请求的接口，其 RIFE 使用 4.26。 [FixDeadFrame](https://github.com/Pondfung/FixDeadFrame)

在 1126 的 16 个指定时间点上，关闭 SDK 自动切镜的 VFG、RIFE 4.25、RIFE 4.26 的平均亮度误差依次为 18.54、16.68、16.84 灰阶。GIMM-VFI 从 720p 生成再放回 1080p，平均误差为 16.27 灰阶，其中 6 个时间点优于其他三条路径。这轮 GIMM-VFI 用时 28.27 秒，包含模型加载和样本读取。遮挡漏报位置 311 的误差依次为 81.38、82.27、82.18 和 80.37 灰阶，四条路径的输出都与真帧相差很大。本轮只比较固定锚点上的局部生成结果。逐帧对照见同目录 `rife-comparison.json` 与 `gimm-comparison.json`。 [RIFE 4.26 权重](https://github.com/HolyWu/vs-rife/releases/expanded_assets/model)

比较 FixDeadFrame 的修复规则时，固定引擎版本、输入精度、切点、待修帧和时刻，记录各规则选择的前后锚点。比较引擎时，再固定锚点与规则。备用引擎按需加载并复用，分别记录冷启动和后续修复的耗时。只有多段真实快镜头在逐帧及正常速度复看中稳定改善、且原帧和时间轴保持正确，才接入相应部分。

## 外部项目的处理办法

- **Veyra-NRVideo 在应用层判断切镜。** 启用自有检测时关闭 SDK 自动切镜。它在 GPU 上对相邻原帧计算亮度差和直方图差，每对只判断一次，结果供所有子帧共用。真切镜时用原帧代替插值。这个设计可以借鉴到离线导出，检测取样和阈值仍需用 FrameLab 的素材验证。 [Veyra VFG 源码](https://github.com/Likely7/Veyra-NRVideo/blob/main/src/pipeline/VfgBackend.cpp#L291-L315)
- **Veyra 另有准星保护导致的背景锁帧。** 2.2.1 改用准星形状的局部合成。其 1440p 录屏中，VFG 2× Medium 和 High 各检查 159 张生成帧，两档的背景锁帧均从 75 张降为 0。排查时若只有 HUD 周围卡住，再考虑类似的局部遮罩。 [Veyra 2.2.1 发行说明](https://github.com/Likely7/Veyra-NRVideo/releases/tag/v2.2.1)
- **同名 FrameLab 项目将 2× 作为起点。** 项目提醒高倍率可能产生严重伪影。一段 VFG Medium 2× 录屏有 437 组完整原帧／插帧／原帧，未发现插帧逐像素等于原帧。该记录只验证了像素不同，作者仍建议查看遮挡、轮廓与 HUD。 [项目说明](https://github.com/tomik520i/FrameLab) · [逐帧样例](https://github.com/tomik520i/FrameLab/blob/main/examples/2026-11-20/README.md)
- **ComfyUI 给每张输出帧独立存储。** 节点在下一次调用前复制 DLPack 输出，并提供切镜开关和原生倍率模式，可以用作独立调用对照。 [ComfyUI VFG 节点](https://github.com/Comfy-Org/ComfyUI_Nvidia_VFX_Nodes#rtx-video-frame-generation) · [NVIDIA Python API](https://docs.nvidia.com/maxine/vfx-python/latest/api.html#nvvfx.VideoFrameGeneration)

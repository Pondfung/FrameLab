# 离线视频超分与插帧选型与开发计划

2026-11-24 · Windows 11 · RTX 5070 12 GB · 已按用户提供的五段素材更新

## 1. 首版方向

**BasicVSR++ 为超分核心，GIMM-VFI-R-P 为插帧核心。** SeedVR2 3B INT8 与 Practical-RIFE 4.25 同场评估，保留为可选引擎。核心优先接入，实际默认预设按素材和本机测试结果决定。BasicVSR++ 适合先验证对脸、旗字等原有细节的保留。GIMM-VFI-R-P 优先验证大运动和遮挡时的插帧。两条核心路径都需要通过 5070 的独立 CUDA 环境和自己的镜头 A/B。

首版面向本地逐行、方形像素、8-bit SDR、恒定帧率视频，支持只超分、只插帧和串联。按现有素材先做 **1080p 24→48**，再测 1080p→1440p/2160p 的放大。两段已经是 4K 编码的素材优先验证原分辨率插帧及切镜。另外从其中派生低清输入，用对应的 4K 帧做超分参考。原始制作分辨率未知。效率只记录，画质、长跑的显存与恢复能力作为验收项。

## 3. 四个引擎的取舍

- **核心超分 · BasicVSR++。** 用 vs-basicvsrpp 跑 REDS4（model 0）和 Vimeo90K bicubic（model 1）的短片对照。常用超分权重固定 4×，因此 1080p→4K 需要按等效 7680×4320 分块重建，再缩到输出尺寸。先用 960×540→3840×2160 真值实验验证引擎，再用 1080p 小片验证实际目标尺寸，并记录峰值显存。利用时间分块、带边缘上下文的空间分块和 CPU 缓存，在旗字、头发等跨分块区域检查拼缝。若目标是既有 4K 的去压缩，可独立评估同家族固定 1× 的压缩增强权重，与超分权重分别记录。 [BasicVSR++ 作者仓库](https://github.com/ckkelvinchan/BasicVSR_PlusPlus) · [vs-basicvsrpp 权重与分块参数](https://github.com/HolyWu/vs-basicvsrpp/blob/master/vsbasicvsrpp/__init__.py)
- **备用超分 · SeedVR2 3B INT8。** 用 ComfyUI 原生模板直出共同目标尺寸，和 BasicVSR++、Lanczos 同场。素材较软、压缩或需要直出 1440p/2160p 时作为候选，逐镜检查脸、字、纹理发生漂移的情况。若显存不足先调整时序分批、VAE 分块和卸载。按本机实测决定是否配置为该类素材的常用预设。 [SeedVR2 论文](https://arxiv.org/abs/2506.05301) · [ComfyUI 原生视频模板](https://docs.comfy.org/tutorials/utility/seedvr2)
- **核心插帧 · GIMM-VFI-R-P。** 作者默认的 RAFT 感知版，支持任意时间位置。原始示例用 PyTorch 1.13/CUDA 11.6。优先用现代 Blackwell CUDA 环境跑作者认可的 Kijai 集成，先验证 CuPy 算子，随后测试 1080p 2×。作者的 4K 8× 示例用 V100、光流尺度 0.25、10922 MiB，针对 5070 另测 4K 2×，按尺度和精度记录显存、飞翅、砂尘、轮廓与高反差细线。任意时间插值能力留给通过 2× 质量门槛后的 24→60 等目标。 [GIMM-VFI 作者仓库](https://github.com/GSeanCDAT/GIMM-VFI) · [Kijai 的模型封装](https://github.com/kijai/ComfyUI-GIMM-VFI)
- **备用插帧 · Practical-RIFE 4.25。** 使用 vs-rife 的 4.25 权重，在同样的切点、尺寸、颜色、输出帧率上与 GIMM-VFI 对比。4K 可以测试降低内部光流尺度，模型实现的输入输出尺寸仍是全帧。尺度改变对细小物体的影响要盲看。RIFE 可用于 GIMM-VFI 的某些失败镜头或显存不足的作业，并保留原帧延展作为硬切、重复帧和明显形变的处理选项。 [Practical-RIFE 作者仓库](https://github.com/hzwer/Practical-RIFE) · [vs-rife 参数](https://github.com/HolyWu/vs-rife/blob/master/vsrife/__init__.py)

两段 1080p 源缺少 primaries、transfer、matrix 和 range 标签，先将 BT.709 limited 作为可追踪假设，对照原片暗部及灰阶并允许覆盖。其余三段明确标记 BT.709 limited。保留原音轨 PTS 和现有尾差，整轨复制时用流时长检查。首尾不同长是这批真实测试的一部分。完全重复的相邻帧可跳过模型直接延展，近似重复仍保留原时间线并预览。

### 已准备的基线

以下三段已用本机 FFmpeg 派生为 FFV1 文件，已读回核对尺寸、帧率和帧数。帧号从 0 开始，起始帧计入。PSNR/SSIM 是全帧各平面汇总，另需按局部纹理做盲看。

| 对照短片 | 派生与评分方式 | 无模型基线 |
| --- | --- | --- |
| 虞姬，起始帧 30，48 帧 | 4K 以 Lanczos 降到 960×540，恢复到 3840×2160 与源帧比较 | Lanczos 44.35 dB / SSIM 0.9910 |
| 陈汤，起始帧 52，48 帧 | 同上 | Lanczos 54.61 dB / SSIM 0.9975 |
| 白鹤，起始帧 60，72 帧 | 每两帧留前一帧，派生 1080p12，重建 24 fps。只给前后有锚点的 35 个缺失帧计分 | 原帧延展 27.90 dB / SSIM 0.9396 |

《陈汤》这一段 Lanczos 基线已很高，评估模型时同时查看局部沙地、毛发、装备和面部，并补更富纹理的镜头。两段 4K 源可追加一份可控压缩的 540p 派生片，区分干净降采样与压缩修复。基线是用来做 A/B 的起点。四个模型尚待推理和评分。

### 比较顺序

1. **先测插帧。** 三段 1080p 用 24→48，比较原帧延展、GIMM-VFI-R-P、RIFE 4.25。重点检查快速遮挡、跨镜和原锚点保持。两段 4K 先选 1～2 秒做原尺寸显存试跑，再决定整段。按源视频显示时长保留末帧区间，完整视频在 48 fps 应分别得到 482、722、432、820、966 帧。
2. **再测超分。** 在 540p 派生片上比较 Lanczos、BasicVSR++ 与 SeedVR2。按与最终项目相同的色彩处理，测试三段 1080p 的实际 1440p/2160p 目标，同尺寸输出，另留纯缩放基线。4K 输入保留现有尺寸作为首版日常预设。
3. **最后串联。** 固定目标尺寸、帧率、切点和编码，在两段入围镜头对比「插帧→超分」、「超分→插帧」、「只超分」和「只插帧」。单引擎组用原帧延展或 Lanczos 补齐另一维。先试源尺寸插帧，减少 GIMM-VFI 处理高分辨率画面的显存压力。只跑画质/显存已通过的组合。评分包含脸与字形稳定性、飞翅/细边是否重影、颜色呼吸、块边和跨切镜眼见伪影。保留正常速度盲看、关键位置逐帧和峰值显存数据。
4. **设默认门槛。** 核心能在实测显存预算内稳定跑完，且对应场景盲看达到可接受或改善，再设为默认。跨切镜融合、明显改写主体、周期偏色、掉帧和音画偏移会使对应预设继续调整。备用模型在某类素材稳定更好时，可以把该预设指向备用模型。保留核心和备选引擎的独立入口与测试记录。

## 5. 工具架构

**Python CLI 作业控制层 + FFmpeg/ffprobe + 独立模型工作进程。** BasicVSR++ 先通过 VapourSynth 验证，GIMM-VFI-R-P 先通过受维护的 ComfyUI 集成验证，再封装可接收工具提供的时间位置与切镜信息的推理入口。SeedVR2 使用 ComfyUI 原生模板并固定工作流 JSON。RIFE 使用 Torch/VapourSynth 工作进程。命令行支持 probe、preview、run、resume 四个入口。交付 MVP 时沿用原型已验证的后端。每个适配器声明支持的尺寸、帧率、像素格式与精度，接收同一作业计划下的镜头分块和输出路径，返回实际使用的参数、产物及帧数。作业控制层负责验证与提交，模型进程只写当前分块的临时路径。 [ComfyUI 本机 API 路由](https://docs.comfy.org/development/comfyui-server/comms_routes) · [FFmpeg 媒体流处理](https://ffmpeg.org/ffmpeg.html)

1. **Probe 与计划。** 获取帧率、time base、旋转、色域/传递/矩阵/range、视频帧 PTS、音频起点、字幕和容器信息。计划保存目标宽高/帧率、走哪条模型路径、切镜点、分块边界和输入指纹。切镜用 FFmpeg 场景检测或画面差异给候选，允许手工修正闪光、渐变以及生成片局部形变。 [FFmpeg 滤镜文档](https://ffmpeg.org/ffmpeg-filters.html)
2. **时间线与颜色。** 用有理数算帧时间。24→48 的原帧位于目标网格，保留锚点。24→60 的部分源 PTS 不落在目标网格，对每个输出时刻从相邻源帧和实际 t 做插值，精确命中的时刻直接取源图。在切镜之间保持切点前的帧，到点切换。尾部按源帧显示区间延展至目标时长。颜色转换显式使用像素格式、原色、传递、矩阵和 range。旧片的 BT.601 与常见 BT.709 区分，颜色标记缺失使用可记录的假设或用户覆盖。固定模型的 RGB 输入范围，插帧前后用色卡和暗场测交替偏色。
3. **模型与缓存。** 超分处理一个镜头内的有上下文分块，插帧依据同一份时间计划读取相邻帧。相邻分块带重叠上下文，优先裁掉边缘帧/重叠帧并只写一次。其保留范围通过对照实验定。阶段间使用分段 FFV1/MKV 或保留时间戳清单的无损帧，明确像素格式与转换点。每 GPU 一项推理工作，按阶段释放模型，再启动下个模型。每段保留实际引擎、精度、分块和光流尺度。备用引擎作为镜头重跑选项，显存不足时如需换引擎，由用户选择或按预设策略整镜头重算。OOM 先释放进程并重试记录过的低显存方案，例如更小块、卸载或分块。改变权重、输出尺寸等画质参数时报告并记录在任务配置中。
4. **作业恢复与成片。** 每个作业留配置、模型权重版本/校验值、镜头和分块列表、完成标记、日志与输出检查结果。块先写临时文件，经尺寸/帧数/可读性校验后原子提交。恢复时校验输入指纹和参数，复用相符的完整块。同一作业加锁，取消后保留已确认块，按设置回收缓存。成片先写临时路径，复核时长、时间基和媒体流后提交，避免覆盖已有成片。输出仅重编码视频。支持容器兼容时复制原始音频/字幕，保留原时间偏移。不兼容可选 MKV 或明确指定转换。用户提供的样本按原音频与视频各自的末端核验，保留已有的轨道尾差。
5. **界面。** CLI 验收后加 PySide6 窗口，支持拖入文件、选预设与输出、同步预览前后、镜头级跳过/重跑、队列进度、暂停后恢复以及打开产物。Python 继续管理作业，UI 调命令行接口。输出首版提供 H.264 MP4 和 FFV1 MKV 两类，后续按片源需求增加 HEVC 与更多容器选项。

## 6. 实施节奏与验收

| 阶段 | 产出 | 验收 |
| --- | --- | --- |
| P0 · 1～2 天 | 独立 CUDA 环境、四个引擎的最小推理、锁定首轮输入和参考 | RTX 5070 上的 CUDA 运算通过，先做少量帧探针，再让 BasicVSR++ 完成一个 540p→4K 分块短段、GIMM-VFI 完成一个 1080p 2× 短段。记录峰值显存和实际参数 |
| P1 · 2～3 天 | 切镜、时间线、四引擎适配与样片评估 | 完成上述 A/B。至少一条 1080p48 路径通过整段验收。记录 4K 原尺寸插帧的分辨率和上下文上限 |
| P2 · 2～4 天 | 分块、持久化作业、失败恢复、成片音轨与字幕映射 | 五段先全量跑。另选 1 分钟和 10 分钟以上长片验证。中断后仅重算未完成块，无缺帧、重复块或可见拼缝。输出的相对音画偏移和轨道尾差与输入相符 |
| P3 · 2～4 天 | PySide6 前后预览、作业队列、预设与导出 | 可拖入素材、看同步 A/B、按镜头更换引擎/跳过、导出并重开程序恢复 |
| P4 · 按样片效果推进 | 24→60、4×、4K 长片、VFR/10-bit/HDR 等 | 逐项测实际输入与资源峰值。7B、FlashVSR+、RealBasicVSR、LDF-VFI 等作为后续扩展候选 |

时间是开发工作量粗估，下载、兼容性排查与渲染耗时单独记录。当前完成素材核查、场景抽帧与无模型基线。四个模型的画质排名、显存峰值及 4K 长跑能力待验证。
